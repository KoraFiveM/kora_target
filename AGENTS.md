# qbtarget resource guide

## Purpose
A fresh targeting engine, built on `qblib` rather than reimplementing raycasting/zones/menus from scratch. One resource, no separate proxy resources — it also directly answers to `exports['qb-target']:...` and `exports.ox_target:...`, translating those real public APIs into calls against `Target.*` (this resource's own native implementation). See "Compatibility mechanism" below for how that actually works, and `client/compat/qb-target.lua`/`client/compat/ox-target.lua` for the exact mapping tables.

## File layout
- `config.lua` — keybinds, tick rates, distance defaults.
- `client/state.lua` — the core data model (`Target.registrations`/`byEntity`/`byModel`/`byGlobalType`/`byGlobalBone`) and every public `add*`/`remove*` function.
- `client/sprites.lua` — distance-culled, display-only `shared/info` zone sprites. It iterates `Target.byZone`, never the game entity pool, and has no raycast work; `drawSprite = false` opts one zone out.
- `client/loop.lua` — keybinds, the main tick thread, candidate resolution against the raycast hit and current zones, prompt drawing, and Alt-release dispatch. While Alt is held, the prompt remains pointer-free; releasing it dispatches one available option immediately or opens `QB.nui.openMenu` after targeting has ended for multiple options. The latter intentionally takes NUI focus so the player can choose with mouse or keyboard without disrupting camera look while aiming.
- `client/exports.lua` — `exports('name', Target.name)` for qbtarget's own native function names, explicit rather than generated (unlike qblib's own `build/finalise.lua`) so it's directly auditable against the compat files' mapping tables.
- `client/compat/qb-target.lua`, `client/compat/ox-target.lua` — translate the real qb-target/ox_target APIs onto `Target.*` and register them under those resource identities (see below). The qb-target bridge uses the manifest-loaded PolyZone classes for genuine legacy zone return objects, then registers their predicates with the native engine. Each bridge calls `Target.*` **directly**, not through `exports.qbtarget:...` — they run in the same resource, so there's no reason to pay for a cross-resource round trip internally.
- `server/server.lua` — the optional `runServerAction`/`registerServerAction` relay.

`fxmanifest.lua` first loads upstream's PolyZone classes, then lists `client/state.lua`, `client/sprites.lua`, `client/loop.lua`, `client/exports.lua`, and the two `client/compat/*.lua` files explicitly — not a glob. Alphabetic glob order would load `exports.lua` before `state.lua` ever defines `Target.addEntity`, the exact problem qblib's own `fxmanifest.lua` documents for why `local/**` isn't a single glob there either. The sprite loop and compat files only need to load after `state.lua` (they reference `Target.*`), so their order relative to `loop.lua`/`exports.lua` doesn't matter.

## Export strategy: plain exports, not qblib's finalise.lua pattern
qblib auto-generates exports from every `QB.<module>.<fn>` entry because it has many modules and a growing function count where hand-listing would rot. qbtarget's own native surface is small and fixed (~16 functions), and it's a clear, greppable `exports('name', fn)` list (`client/exports.lua`) that's easy to keep honest against `Target.*`. This also matches how the real qb-target/ox_target declare their own exports.

## Compatibility mechanism: `provide` + manual export registration
`fxmanifest.lua` declares `provide 'qb-target'` and `provide 'ox_target'`. On its own, `provide` only satisfies **another resource's** `dependency 'qb-target'`/`dependencies` check — it does **not** make `exports['qb-target']:Fn()` resolve to code running here. That resolution is itself just an event under the hood: `exports('name', fn)` is sugar for `AddEventHandler(('__cfx_export_%s_%s'):format(GetCurrentResourceName(), name), function(setCB) setCB(fn) end)`. Both compat files duplicate a small `provideExport(providedResource, exportName, func)` helper that registers that exact event under the STRING `'qb-target'`/`'ox_target'` instead of this resource's real name — that's what actually makes `exports['qb-target']:AddBoxZone(...)`/`exports.ox_target:addBoxZone(...)`, called from any other resource, reach the functions defined in `client/compat/qb-target.lua`/`client/compat/ox-target.lua`. `provide` is kept anyway since it's still the correct signal for dependency resolution — the two mechanisms serve different purposes and neither substitutes for the other.

Because `qbtarget`, `'qb-target'`, and `'ox_target'` are three independently-registered event namespaces (`__cfx_export_qbtarget_addBoxZone` vs `__cfx_export_ox_target_addBoxZone` vs `__cfx_export_qb-target_AddBoxZone` are different events), qbtarget's own native `addBoxZone`/`addModel`/etc. (registered via plain `exports()` in `client/exports.lua`) and the ox_target-compat `addBoxZone`/`addModel`/etc. (registered via `provideExport('ox_target', ...)` in `client/compat/ox-target.lua`) can share the same literal name with zero collision, even though they run different translation logic — this is not the same failure mode a single flat export table would have.

## Ownership subtlety (read before touching zone registration code)
`Target.addBoxZone`/`addSphereZone`/`addPolyZone` call `QB.zones.box/sphere/poly(opts)` on behalf of whatever resource originally registered the zone — which could be any third-party consumer (a shop script, etc.), reached either directly (`exports.qbtarget:addBoxZone`) or through one of the compat layers (`exports['qb-target']:AddBoxZone`, `exports.ox_target:addBoxZone`). qblib's own `QB.zones.box/sphere/poly` resolve the zone's owning resource via `GetInvokingResource()` **at that call site**, which is `"qbtarget"` itself (the direct caller into qblib), never the original external consumer — confirmed by reading `qblib/modules/zones/client.lua`: the public constructors call `createZone(type, opts, initShape)` with no resource override (only the internal zone-creator flow passes one). So qblib's own cleanup-on-stop only ever fires when qbtarget itself stops, never when the real consumer resource does.

`Target.ownership` is what fixes this: every `add*`/zone constructor captures `GetInvokingResource() or GetCurrentResourceName()` **before** calling into `QB.zones.*`, and tracks the registration id against that real owner. Because the compat layers call `Target.addBoxZone` etc. **directly** (a plain same-resource Lua call, not a second `exports()` hop), `GetInvokingResource()` inside `Target.addBoxZone` still reflects the ORIGINAL external caller regardless of which of the three identities (`qbtarget`/`qb-target`/`ox_target`) it went through — there's exactly one export-boundary crossing total, from the external consumer into this resource. (A separate-shim-resource design would have gotten this wrong: a second hop from the shim into `exports.qbtarget:addBoxZone` would have made `GetInvokingResource()` resolve to the shim's own name, not the real original caller — one of the reasons this single-resource design replaced that one.) `Target.destroyRegistration`'s `zone` branch is what proactively calls `zoneHandle.remove()` when that real owner stops — qblib's own sweep is never a substitute for this, it only ever cleans up qbtarget's own registrations, not qbtarget's callers'.

`Target.ownership` is a **local, hand-rolled** registry (`client/state.lua`, a `byResource`/`ownerOf` table pair swept on `onClientResourceStop`) rather than a `QB.resources.registry` instance fetched cross-resource, deliberately. That factory's returned `track`/`untrack`/`owner` values are plain Lua closures living inside qblib's own environment, and while FXServer's exports boundary generally supports returning function references across resources, `qblib/local/resources/AGENTS.md`'s own "Consumers" list only ever documents this factory being consumed **from within qblib itself** — every listed consumer (`entities`, `zones`, `cache`, `blips`, `callback`, `events`) is an internal qblib module, none cross-resource. Rather than rest a leak-sensitive mechanism (mis-tracked ownership silently leaves zones/registrations behind forever) on an unconfirmed usage pattern, qbtarget mirrors qblib's own `local/resources/client.lua` shape almost verbatim, entirely locally — same idempotency guarantee (an `onClientResourceStop`-driven `destroyRegistration` clears `ownerOf[id]` before calling itself, so a subsequent `Target.ownership.untrack(id)` inside `destroyRegistration` is a harmless no-op, exactly like qblib's own `zoneOwnership.untrack` behaves when called from within its own sweep).

`Target.byZone` (`client/state.lua`) is a flat `id -> true` set of every zone-kind registration, populated by `addBoxZone`/`addSphereZone`/`addPolyZone` and cleared in `destroyRegistration`'s `zone` branch. `client/loop.lua`'s `zoneRegistrationsAt(point)` walks it each resolve and tests `registration.zoneHandle.contains(point)` directly against that tick's raycast hit — no zone `data` stamping or a second lookup table needed, since the registration id is already the table key.

## Zone visibility and debugging
`Config.target.debug = true` is a global override passed to qblib's native zone
constructors, so every target zone gets its normal qblib debug outline; a
single `debug = true` zone works without the override. `client/sprites.lua`
adds a separate player-facing visual: it draws the configured streamed texture
sprite at `registration.spriteCoords` for nearby coordinate zones. It uses a
500ms idle cadence and moves to frame cadence only while a visible nearby
sprite is being drawn. Do not extend this to scan model/global registrations:
they have no one anchor and a game-pool scan would undermine the target
resource's performance guarantees. Native and ox_target-compatible zone calls
accept `drawSprite = false` for a per-zone opt-out.

## Candidate resolution (client/loop.lua)
- `classifyEntity` uses live-entity natives (`GetEntityType`/`IsPedAPlayer`) to answer "what type is this entity handle", deliberately **not** qblib's `modules/entities`' `detectEntityType` — that function classifies a **model hash** to decide how to spawn something, a different operation on a different input than classifying an already-existing live entity. `GetEntityType == 0` is rejected before `GetEntityModel`; falling back from two false `IsEntityA*` checks to "object" would incorrectly let an unresolved handle through.
- Bone-scoped options (`option.bones`, or a `globalBone` registration's own bone list) only ever match against an entity candidate (`entity` present) — a zone candidate passes `entity = nil` into `appendCandidates`, so `boneMatches` returns `false` outright for a bone-scoped option even though a zone candidate does have an aim point (the raycast hit) now; there's simply no entity to read a bone position off of.
- The adaptive resolver uses squared-distance rejection before bone matching, then the caller's `canInteract` (which may be arbitrarily expensive and is `pcall`-wrapped). It caches registration-index lookups for a stable aimed entity and bone locations for one resolver pass, and `canInteract` results for at most `Config.target.canInteractCacheMs`; none of these caches are authoritative.
- `Config.target.demo` must remain opt-in. Its global ped/vehicle registrations are useful for development but add evaluation work to every aimed entity in production.
- Zone-based candidates are matched against the raycast hit point (`zoneRegistrationsAt(hitCoords)` in `client/loop.lua`, via each zone's own `zoneHandle.contains(point)`), not the player's own position — aiming at a point inside a zone is enough, standing inside it is not required. This is a deliberate departure from `QB.zones.getInside`-style position tracking (and from how some legacy qb-target/ox_target versions behave) precisely because a targeting tool should key off where the player is looking. Zone candidates are still gated behind the hold key and require an actual raycast hit (`hit and hitCoords`), same as entity/model candidates.

## Job/gang/item enforcement
qbtarget's own native format (`docs.md`'s "Opaque fields" section) still never interprets `item`/`job`/`gang`/`groups` — that's a deliberate, permanent property of the native resolver staying framework-agnostic, not something qb-core's arrival changes.

The **qb-target compat shim** (`client/compat/qb-target.lua`) is different: it now enforces `job`/`excludejob`/`jobType`/`excludejobType`/`gang`/`excludegang`/`item`/`citizenid` for real, ported entirely from real qb-target's own `JobCheck`/`JobTypeCheck`/`GangCheck`/`CitizenCheck`/`ItemCheck` (`qbcore-fivem/qb-target`'s client.lua "QBCore init" section). This exists because qbcore does now (`resources/[test]/qbcore`, `provide 'qb-core'`) — the shim `pcall`s `exports['qb-core']:GetCoreObject({'Functions'})` once at load time and tracks `PlayerData` via `QBCore:Client:OnPlayerLoaded`/`OnPlayerUnload`/`OnPlayerUpdated`, exactly like real qb-target's own client.lua does. Every filter is wrapped into a synthesized `canInteract` (`makeCanInteract`) that ANDs with the option's own `canInteract`, matching real qb-target's `CheckOptions` order. If qb-core genuinely isn't running (this shim has no hard dependency on it), enforcement is skipped entirely and a registration-time warning fires instead — the same graceful degradation this file used to always fall back to.

This was a confirmed, security-relevant compat bug before the fix: `jobType` wasn't even a recognized field (silently dropped, no warning at all — unlike `job`/`gang`/`item`, which at least warned), so every `Config.UseTarget = true` police interaction zone in real `qb-policejob` (duty sign-in, stash, trash, fingerprint, evidence — all keyed on `jobType = 'leo'`) was reachable by any player.

The ox_target compat (`client/compat/ox-target.lua`) is unaffected — real ox_target's own filtering model is `groups`-based against ox_core, a different framework this repo also doesn't run; that stays unenforced by design, same as `docs.md` describes.

## Server actions
`server/server.lua`'s `qbtarget:server:runAction` callback replies with `(ok, ...)` directly — `true` plus the registered action handler's own return values, or `false` plus a reason string. This relies on `qblib`'s `QB.callback` module forwarding a handler's return values in full, end to end (multi-value support added after this resource was first built — an earlier version of this file hand-rolled a `{ok, result?, error?}` envelope table to work around `QB.callback` only forwarding a single value; that workaround is gone now that the underlying limitation is fixed in qblib itself). `client/state.lua`'s `Target.runServerAction` is now a thin pass-through — `return QB.callback.trigger(...)` — with no unpacking of its own needed.

## Testing
`test/run.sh` runs `test/smoke/runtime.lua` against a standalone `lua` interpreter (not a running FiveM client), following `qblib/test/harness.lua`'s own pattern: it stubs every native the resolver touches, loads `config.lua`/`client/state.lua`/`client/loop.lua` with `Config.target.testMode = true` (which makes `client/loop.lua` expose its private resolver functions on `Target._testRuntime` -- see the bottom of that file), and exercises registration-revision cache invalidation, `canInteract` caching, aim-point zone matching, the entity-focused raycast fallback, and stale-entity guarding. It does not drive the `+target`/`-target` commands end to end, since those need a real (or coroutine-faithful) `CreateThread`/`Wait` scheduler that the harness's no-op stubs don't provide. Manual in-game verification is still how the Alt-release/NUI wiring gets exercised.
