# kora_target resource guide

## Purpose
A fresh targeting engine, built on `kora_lib` rather than reimplementing raycasting/zones/menus from scratch. One resource, no separate proxy resources — it also directly answers to `exports['qb-target']:...` and `exports.ox_target:...`, translating those real public APIs into calls against `Target.*` (this resource's own native implementation). See "Compatibility mechanism" below for how that actually works, and `client/compat/qb-target.lua`/`client/compat/ox-target.lua` for the exact mapping tables.

## File layout
- `config.lua` — keybinds, tick rates, distance defaults.
- `client/state.lua` — the core data model (`Target.registrations`/`byEntity`/`byModel`/`byGlobalType`/`byGlobalBone`) and every public `add*`/`remove*` function.
- `client/sprites.lua` — distance-culled, display-only `shared/info` zone sprites. It queries the zone broad phase (`Target.zonesWithin`), never the game entity pool, and has no raycast work; `drawSprite = false` opts one zone out.
- `client/loop.lua` — keybinds, the main tick thread (see "Resolver cost" below), candidate resolution against the raycast hit and current zones, prompt drawing, and Alt-release dispatch. While Alt is held, the prompt remains pointer-free; releasing it dispatches one available option immediately or opens `Kora.interact.open` after targeting has ended for multiple options. That selector remains pointer-free and uses kora_lib's configured scroll/arrow controls plus E to select.
- `client/exports.lua` — `exports('name', Target.name)` for kora_target's own native function names, explicit rather than generated (unlike kora_lib's own `build/finalise.lua`) so it's directly auditable against the compat files' mapping tables.
- `client/compat/qb-target.lua`, `client/compat/ox-target.lua` — translate the real qb-target/ox_target APIs onto `Target.*` and register them under those resource identities (see below). The qb-target bridge returns kora_lib-backed, zone-compatible objects; it also accepts PolyZone objects when the optional compatibility resource is running. Each bridge calls `Target.*` **directly**, not through `exports.kora_target:...` — they run in the same resource, so there's no reason to pay for a cross-resource round trip internally.
- `server/server.lua` — the optional `runServerAction`/`registerServerAction` relay.

`fxmanifest.lua` lists `client/state.lua`, `client/sprites.lua`, `client/loop.lua`, `client/exports.lua`, and the two `client/compat/*.lua` files explicitly — not a glob. Alphabetic glob order would load `exports.lua` before `state.lua` ever defines `Target.addEntity`, the exact problem kora_lib's own `fxmanifest.lua` documents for why `local/**` isn't a single glob there either. The sprite loop and compat files only need to load after `state.lua` (they reference `Target.*`), so their order relative to `loop.lua`/`exports.lua` doesn't matter.

## Export strategy: plain exports, not kora_lib's finalise.lua pattern
kora_lib auto-generates exports from every `Kora.<module>.<fn>` entry because it has many modules and a growing function count where hand-listing would rot. kora_target's own native surface is small and fixed (~16 functions), and it's a clear, greppable `exports('name', fn)` list (`client/exports.lua`) that's easy to keep honest against `Target.*`. This also matches how the real qb-target/ox_target declare their own exports.

## Compatibility mechanism: `provide` + manual export registration
`fxmanifest.lua` declares `provide 'qb-target'` (and `provide 'kora_target'`). It deliberately does **not** provide `ox_target`: `stubs/ox_target` is a real resource with that name, and claiming it from both made `stop ox_target` stop kora_target and its dependents. Resources that declare `dependency 'ox_target'` or check `GetResourceState('ox_target')` need the `stubs/ox_target` placeholder ensured after kora_target; `exports.ox_target:*` works without it. On its own, `provide` only satisfies **another resource's** `dependency 'qb-target'`/`dependencies` check — it does **not** make `exports['qb-target']:Fn()` resolve to code running here. That resolution is itself an event under the hood. Both compat files use `Kora.compat.provideExport` to register that event under the STRING `'qb-target'`/`'ox_target'` instead of this resource's real name — that's what actually makes `exports['qb-target']:AddBoxZone(...)`/`exports.ox_target:addBoxZone(...)`, called from any other resource, reach the functions defined in `client/compat/qb-target.lua`/`client/compat/ox-target.lua`. `provide 'qb-target'` is kept anyway since it's still the correct signal for dependency resolution — the two mechanisms serve different purposes and neither substitutes for the other.

Because `kora_target`, `'qb-target'`, and `'ox_target'` are three independently-registered event namespaces (`__cfx_export_kora_target_addBoxZone` vs `__cfx_export_ox_target_addBoxZone` vs `__cfx_export_qb-target_AddBoxZone` are different events), kora_target's own native `addBoxZone`/`addModel`/etc. (registered via plain `exports()` in `client/exports.lua`) and the ox_target-compat `addBoxZone`/`addModel`/etc. (registered via `provideExport('ox_target', ...)` in `client/compat/ox-target.lua`) can share the same literal name with zero collision, even though they run different translation logic — this is not the same failure mode a single flat export table would have.

## Ownership subtlety (read before touching zone registration code)
`Target.addBoxZone`/`addSphereZone`/`addPolyZone` call `Kora.zones.box/sphere/poly(opts)` on behalf of whatever resource originally registered the zone — which could be any third-party consumer (a shop script, etc.), reached either directly (`exports.kora_target:addBoxZone`) or through one of the compat layers (`exports['qb-target']:AddBoxZone`, `exports.ox_target:addBoxZone`). kora_lib's own `Kora.zones.box/sphere/poly` resolve the zone's owning resource via `GetInvokingResource()` **at that call site**, which is `"kora_target"` itself (the direct caller into kora_lib), never the original external consumer — confirmed by reading `kora_lib/modules/zones/client.lua`: the public constructors call `createZone(type, opts, initShape)` with no resource override (only the internal zone-creator flow passes one). So kora_lib's own cleanup-on-stop only ever fires when kora_target itself stops, never when the real consumer resource does.

`Target.ownership` is what fixes this: every `add*`/zone constructor captures `GetInvokingResource() or GetCurrentResourceName()` **before** calling into `Kora.zones.*`, and tracks the registration id against that real owner. Because the compat layers call `Target.addBoxZone` etc. **directly** (a plain same-resource Lua call, not a second `exports()` hop), `GetInvokingResource()` inside `Target.addBoxZone` still reflects the ORIGINAL external caller regardless of which of the three identities (`kora_target`/`qb-target`/`ox_target`) it went through — there's exactly one export-boundary crossing total, from the external consumer into this resource. (A separate-shim-resource design would have gotten this wrong: a second hop from the shim into `exports.kora_target:addBoxZone` would have made `GetInvokingResource()` resolve to the shim's own name, not the real original caller — one of the reasons this single-resource design replaced that one.) `Target.destroyRegistration`'s `zone` branch is what proactively calls `zoneHandle.remove()` when that real owner stops — kora_lib's own sweep is never a substitute for this, it only ever cleans up kora_target's own registrations, not kora_target's callers'.

`Target.ownership` is a `Kora.resources.registry` instance. kora_lib now documents
cross-resource registry handles as a supported contract and tests callable-table
disposers, matching the shape FiveM uses for exported funcrefs. The registry's
stop sweep clears ownership before invoking `Target.destroyRegistration`, so
the `Target.ownership.untrack(id)` inside that teardown remains an idempotent
no-op on the stop-driven path.

`Target.byZone` (`client/state.lua`) is a flat `id -> true` set of every zone-kind registration, populated by `addBoxZone`/`addSphereZone`/`addPolyZone` and cleared in `destroyRegistration`'s `zone` branch. `client/loop.lua`'s `zoneRegistrationsAt(point, pedCoords)` resolves against that tick's raycast hit by testing `registration.zoneHandle.contains(point)` — no zone `data` stamping or a second lookup table needed, since the registration id is already the table key. It no longer tests *every* zone, though; see "Zone broad phase" below.

## Zone broad phase (client/state.lua)
Testing every zone's `contains` predicate on every resolver tick is fine for a handful of zones and is the resolver's worst scaling behaviour on a real server: a qb-target-compatible install routinely registers hundreds-to-thousands of zones, and this ran 20x/second for the whole time Alt was held. Two exact filters now sit in front of it. **Neither can change which zones match** — they only skip zones that provably cannot.

1. **Reach.** Every zone candidate anchors on the raycast hit itself, so the ped→anchor distance `appendCandidates` tests is *identical for every zone in a given tick*. One comparison of that distance against `Target.maxZoneOptionDistance()` (the largest interact distance any zone option uses, cached against `Target.registrationRevision` because `Target._replaceOptions` can change it) therefore rejects the entire pass. Aiming at something 8m away can never produce a 2.5m zone candidate.
2. **`Target.zonesNear(point, out)`.** A uniform 50m XY grid over each zone's AABB. A zone is inserted into *every* cell its box overlaps, so a point query only reads the **single** cell containing that point — no 3x3 neighbourhood, no radius padding — and the AABB is then re-tested exactly before the real `contains` predicate runs. `Target.zonesWithin(x, y, radius, out)` is the area form the sprite loop uses (it does sweep cells, and de-duplicates, because a wide zone lives in several buckets).

kora_lib's own `modules/zones` keeps a structurally identical grid that kora_target deliberately does **not** reuse: that one answers "which zones are near the PLAYER" for its enter/exit tick, and kora_target resolves against the AIM point instead — and kora_lib exposes no point query over it in any case.
Native kora_target zones therefore pass `trackPlayer = false` to kora_lib. Their handles retain `contains()`/debug/removal behavior, but kora_lib does not insert them into its separate player-position grid or wake its zone tick for them.

**The bounds contract is the part to be careful with.** A bound must fully *contain* its zone: an over-large box costs one wasted exact test, an under-sized one silently makes the zone untargetable. A zone whose extent cannot be derived goes to `zoneUnbounded` and is still scanned every tick exactly as before, so a *missing* bound only ever costs performance. That is why:
- `addBoxZone` uses rotated half-extents (a heading only ever grows the axis-aligned footprint), `addSphereZone` the radius, and `addPolyZone` the XY hull of its points — with an **unbounded vertical band unless `minZ`/`maxZ` were given explicitly**, since kora_lib derives an implicit band from `thickness` against `Config.zones.defaultPolyThickness`, which lives in kora_lib's environment and isn't readable from here. The grid is indexed on XY only, so a tall AABB costs nothing.
- `Target._addCustomZone` takes its bounds as an optional argument, and `Target._zoneBounds(x, y, extentX, extentY, minZ, maxZ)` is the helper the compat bridges build them with.
- `client/compat/qb-target.lua` derives bounds from the **caller's own arguments**, never by reading fields back off a constructed PolyZone object: PolyZone's `scale`/`offset` grow a box beyond the `length`/`width` it was created with, and an AABB that missed that growth would hide the zone. `legacyBoxBounds` returns `nil` outright when `scale`/`offset` are present rather than guessing; the standalone (no-PolyZone) box branch bounds the *scaled* rectangle it actually tests. `AddComboZone` and `AddEntityZone` supply no bounds at all — a combo's sub-shapes are opaque predicates and an entity zone moves.

`Target.hasSpriteZone()` is a counter maintained by the same `registerZone`/`unregisterZone` pair, not a registry walk: `client/sprites.lua` asks twice per frame while anything is drawing, and `drawSprite`/`spriteCoords` are fixed at registration time so a counter cannot drift out of sync with a walk.

## Zone visibility and debugging
`Config.target.debug = true` is a global override passed to kora_lib's native zone
constructors, so every target zone gets its normal kora_lib debug outline; a
single `debug = true` zone works without the override. `client/sprites.lua`
adds a separate player-facing visual: it draws the configured streamed texture
sprite at `registration.spriteCoords` for nearby coordinate zones. It uses a
500ms idle cadence and moves to frame cadence only while a visible nearby
sprite is being drawn. Do not extend this to scan model/global registrations:
they have no one anchor and a game-pool scan would undermine the target
resource's performance guarantees. Native and ox_target-compatible zone calls
accept `drawSprite = false` for a per-zone opt-out.

## Candidate resolution (client/loop.lua)
- `classifyEntity` uses live-entity natives (`GetEntityType`/`IsPedAPlayer`) to answer "what type is this entity handle", deliberately **not** kora_lib's `modules/entities`' `detectEntityType` — that function classifies a **model hash** to decide how to spawn something, a different operation on a different input than classifying an already-existing live entity. `GetEntityType == 0` is rejected before `GetEntityModel`; falling back from two false `IsEntityA*` checks to "object" would incorrectly let an unresolved handle through.
- Bone-scoped options (`option.bones`, or a `globalBone` registration's own bone list) only ever match against an entity candidate (`entity` present) — a zone candidate passes `entity = nil` into `appendCandidates`, so `boneMatches` returns `false` outright for a bone-scoped option even though a zone candidate does have an aim point (the raycast hit) now; there's simply no entity to read a bone position off of.
- The adaptive resolver uses squared-distance rejection before bone matching, then the caller's `canInteract` (which may be arbitrarily expensive and is `pcall`-wrapped). It caches registration-index lookups for a stable aimed entity and bone locations for one resolver pass. Successful `canInteract` results remain uncached by default; failed results use the bounded `Config.target.canInteractFailureCacheMs` cooldown so unavailable options do not rerun every pass. None of these caches are authoritative.
- `Config.target.canInteractCacheMs` defaults to `0`, while `canInteractFailureCacheMs` defaults to `250`. Each option table owns at most one current entry with entity and distance-bucket fields, avoiding formatted-string keys and stale entries accumulated while walking.
- The resolver's per-tick scratch (bone cache, zone candidate ids, zone candidate registrations, and candidate records) is reused across ticks rather than reallocated, and the entity-registration cache and HUD snapshot compare **fields** rather than formatted `"a:b:c"` key strings. Reset replaces the candidate pool before a released selection is handed to an async menu, so captured records are never rewritten underneath it.
- `Config.target.demo` must remain opt-in. Its global ped/vehicle registrations are useful for development but add evaluation work to every aimed entity in production.
- Zone-based candidates are matched against the raycast hit point (`zoneRegistrationsAt(hitCoords)` in `client/loop.lua`, via each zone's own `zoneHandle.contains(point)`), not the player's own position — aiming at a point inside a zone is enough, standing inside it is not required. This is a deliberate departure from `Kora.zones.getInside`-style position tracking (and from how some legacy qb-target/ox_target versions behave) precisely because a targeting tool should key off where the player is looking. Zone candidates are still gated behind the hold key and require an actual raycast hit (`hit and hitCoords`), same as entity/model candidates.

## Resolver cost (client/loop.lua)
The tick thread is not a per-frame loop and must not become one: raycasts and option resolution run at `Config.target.tickAcquire`/`tickActive` (50ms, 20Hz) while the key is held. Three things keep a held key from being expensive:

- **The broad `511` ray runs on each real scan; the `26` entity fallback is conditional and rate-limited.** `raycastTarget` snapshots the camera/ped once, starts the fallback only when the broad result has no entity, and caps fallback frequency with `Config.target.entityProbeInterval`. This avoids continuously firing two shape tests at ordinary world geometry; the less-common fallback may take one additional settle frame.
- **The zone pass is a grid query, not a scan.** See "Zone broad phase" above.
- **`aimIsStatic` lets a tick reuse the previous resolve** while the camera and the ped are *bit-for-bit* motionless. Exact equality means any real aim adjustment resolves on the next tick. `Config.target.staticRefresh` caps reuse over a hit/candidate, while `staticMissRefresh` permits a longer quiet window over empty space. Diagnostic counter writes are skipped entirely unless diagnostics are enabled.

## Job/gang/item enforcement
kora_target's own native format (`docs.md`'s "Opaque fields" section) still never interprets `item`/`job`/`gang`/`groups` — that's a deliberate, permanent property of the native resolver staying framework-agnostic, not something qb-core's arrival changes.

The **qb-target compat shim** (`client/compat/qb-target.lua`) is different: it now enforces `job`/`excludejob`/`jobType`/`excludejobType`/`gang`/`excludegang`/`item`/`citizenid` for real, ported entirely from real qb-target's own `JobCheck`/`JobTypeCheck`/`GangCheck`/`CitizenCheck`/`ItemCheck` (`qbcore-fivem/qb-target`'s client.lua "QBCore init" section). This exists because kora_core does now (`resources/[test]/kora_core`, `provide 'qb-core'`) — the shim reads `exports.kora_core:getPlayerData()` and converts its native grade levels to the existing qb-target filter format, then tracks `PlayerData` via `QBCore:Client:OnPlayerLoaded`/`OnPlayerUnload`/`OnPlayerUpdated`, exactly like real qb-target's own client.lua does. Every filter is wrapped into a synthesized `canInteract` (`makeCanInteract`) that ANDs with the option's own `canInteract`, matching real qb-target's `CheckOptions` order. If qb-core genuinely isn't running (this shim has no hard dependency on it), enforcement is skipped entirely and a registration-time warning fires instead — the same graceful degradation this file used to always fall back to.

This was a confirmed, security-relevant compat bug before the fix: `jobType` wasn't even a recognized field (silently dropped, no warning at all — unlike `job`/`gang`/`item`, which at least warned), so every `Config.UseTarget = true` police interaction zone keyed on `jobType = 'leo'` was reachable by any player.

The ox_target compat (`client/compat/ox-target.lua`) enforces `groups` (string / array / `{name=minGrade}`) against the same kora_core PlayerData via `Target._playerData()` (job and gang names, convar `kora_target:oxGroups 0` to disable); `items`/`anyItem` are enforced through `exports.kora_inventory:HasItem(name, amount)` (no kora_inventory = never denies, warned once). `offset`/`offsetSize`/`absoluteOffset` (alias `offsetAbsolute`) gate entity/model options on the aim point (ignored for zones, as upstream). `openMenu`/`menuName` implement sub-menus with a `builtin:goback` global entry; the menu persists across presses until go-back/`'home'` or `kora_target:oxMenuTimeoutMs` (default 15000, 0 = never). Selection follows upstream order `onSelect` > `export` (`exports[option.resource or registeringResource][export](nil, response)`) > `event` > `serverEvent` > `command` (`ExecuteCommand`), and the response is the option minus `icon/groups/items/canInteract/onSelect/export/event/serverEvent/command` plus `entity/zone/coords/distance`. `isActive` returns `Target.active` (whole targeting session, like upstream `state.isActive()`). Box, sphere and poly zones are all removable by `name`. Its `canInteract` receives ox_target's `(entity, distance, coords, name, bone)` (the resolver passes the aim point as a 4th argument; `bone` is always nil), `removeModel`/`removeLocalEntity` accept option names, and options may be one bare table. `stubs/ox_target/` is the manifest-only `[compat]/ox_target` placeholder (see its README).

## Pending SpawnPed configs and stock commands
Configs passed to `SpawnPed` without `spawnNow` are spawned on `QBCore:Client:OnPlayerLoaded` (and at resource start if `LocalPlayer.state.isLoggedIn`); `OnPlayerUnload` deletes spawned peds, which respawn on the next load, as upstream. `+playerTarget`/`-playerTarget` are plain commands aliasing the `target` keybind press/release.

## Server actions
The qb-target `SpawnPed` compatibility helper uses kora_lib's bounded
`Kora.stream.loadModel` and `Kora.stream.loadAnimDict` helpers. Bad or unavailable
assets fail cleanly, streaming requests are released, and a partial ped/config
is rolled back instead of leaving a caller suspended forever.

`server/server.lua`'s `kora_target:server:runAction` callback replies with `(ok, ...)` directly — `true` plus the registered action handler's own return values, or `false` plus a reason string. This relies on `kora_lib`'s `Kora.callback` module forwarding a handler's return values in full, end to end (multi-value support added after this resource was first built — an earlier version of this file hand-rolled a `{ok, result?, error?}` envelope table to work around `Kora.callback` only forwarding a single value; that workaround is gone now that the underlying limitation is fixed in kora_lib itself). `client/state.lua`'s `Target.runServerAction` is now a thin pass-through — `return Kora.callback.trigger(...)` — with no unpacking of its own needed.

## Testing
`test/run.sh` runs `test/smoke/runtime.lua` against a standalone `lua` interpreter (not a running FiveM client), following `kora_lib/test/harness.lua`'s own pattern: it stubs every native the resolver touches, loads `config.lua`/`client/state.lua`/`client/loop.lua` with `Config.target.testMode = true` (which makes `client/loop.lua` expose its private resolver functions on `Target._testRuntime` -- see the bottom of that file), and exercises registration-revision cache invalidation, `canInteract` caching, aim-point zone matching, the entity-focused raycast fallback, stale-entity guarding, the zone broad phase (grid rejection, rotated-box bounds, the reach filter, unbounded custom zones, compat-supplied bounds), the sprite counter, and `aimIsStatic`'s reuse window. It does not drive the `+target`/`-target` commands end to end, since those need a real (or coroutine-faithful) `CreateThread`/`Wait` scheduler that the harness's no-op stubs don't provide. Manual in-game verification is still how the Alt-release/NUI wiring gets exercised.

## Documentation

User-facing documentation lives in `docs/` (Markdown, published via the Kora Docusaurus site, kora_docs_next). Read `docs/index.md` first: it is the hub with an overview, features and a documentation map linking every page. Layout: `index.md` (hub), `installation.md`, `how-to-use.md` (examples, security, migration, convars), `commands.md`, `api/` (`index.md`, `target-api.md` for the native `exports.kora_target` functions and server actions, `compatibility.md` for the qb-target/ox_target mappings and the `ox_target` placeholder), and topic pages (`usage.md`, `configuration.md`, `options.md`, `events.md`, `performance.md`, `troubleshooting.md`). Update the page that owns the topic; do not create a second page for the same topic. The pages were restored from the legacy docs site content (KoraFiveM/kora_docs), so keep its tables, examples and console output intact when editing.

When you add, change, or remove a feature, config option, command, export, event, item, permission, or database table/column, update the matching page in `docs/` in the same change. Keep docs accurate to the code; do not document behaviour that does not exist.

Docs rules: plain Markdown with `title`/`sidebar_position` front matter (no `id`/`slug`), relative links only between docs pages, assets inside `docs/`, fenced code blocks with a language, and no raw `<`, `>`, `{`, `}` outside code (pages are parsed as MDX). The release version comes from `fxmanifest.lua`'s `version` field.
